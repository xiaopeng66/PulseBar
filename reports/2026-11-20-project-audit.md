# PulseBar 项目审查报告

审查日期：2026-11-20
审查范围：当前仓库的 C++/MFC 程序、插件管理与下载、构建工作流、Python 工具和测试、配置及文档。
审查结果：修复 1 项任务栏闪烁根因；记录 5 项待处理问题。

## 已修复：任务栏面板周期性闪烁

`CPulseBarDlg::OnTimer` 每 10 秒检查一次任务栏嵌入状态；标记为失败时会关闭并重新创建面板（`PulseBar/PulseBarDlg.cpp:2662-2674`）。初始化代码原先将 `SetParent` 返回空句柄直接判作失败，但 Windows API 在旧父窗口为空时也会合法返回空句柄；同时调用前没有清空 LastError，读取到的错误码可能是旧值。因而窗口实际已经正确嵌入时仍会被标记失败，随后进入定时重建路径。

修复位于 `PulseBar/TaskBarDlg.cpp:1364-1371`：调用前清空 LastError；只在返回空句柄且错误码非零时将 API 调用判失败；并继续检查最终 `GA_PARENT` 是否等于目标任务栏父窗口。回归检查位于 `tools/tests/test_window_lifecycle_guards.py`。

## 编号问题

### F-01 — [P2] 插件商店允许 HTTP 下载并跳过缺失的 SHA-256

**位置：** `PulseBar/PluginStoreDlg.cpp:442-460`；`PulseBar/PluginUpdateHelper.h:37-38`

**证据：** 清单中的 `http://` 与 `https://` 都会原样进入下载函数；安装后只有 `sha256` 非空才比较文件摘要。头文件也明确规定哈希为空时跳过校验。

**影响：** 某个商店条目若配置为 HTTP 且未提供哈希，传输链路上的攻击者可以替换 DLL。通过 PE 架构检查的恶意 DLL 会被放进插件目录，并在 PulseBar 进程内加载执行。当前官方 Magpie 条目使用 HTTPS 和非空 SHA-256，因此此发现针对可被该代码接受的其他/未来清单条目。

**建议：** 安装前强制 HTTPS；官方条目必须提供格式正确的 SHA-256，缺失或无效时拒绝安装。若要支持第三方条目，应把信任和校验要求明确成策略，而不是默认降级为无校验。

### F-02 — [P2] 插件 DLL 下载没有大小或总时限上限

**位置：** `PulseBar/PluginStoreDlg.cpp:103-110, 447-472`

**证据：** 使用 `URLDownloadToFileW` 直接写入插件目录中的临时文件，没有限制写入字节数或总耗时；下载任务随后以 `detach()` 运行，关闭对话框不会取消传输。

**影响：** 失效、错误配置或被控制的下载源可以持续占用磁盘空间或工作线程。窗口关闭后后台任务仍可继续，用户也无法从界面中取消。

**建议：** 使用可报告进度且支持取消的下载接口，在写入时实施明确的最大包大小和总时限，并确保中止时删除临时文件。

### F-03 — [P2] GitHub Actions 依赖使用可移动标签而非不可变提交

**位置：** `.github/workflows/main.yml:13,16,34,41`（其他架构作业重复使用相同方式）

**证据：** `actions/checkout@v7`、`microsoft/setup-msbuild@v3`、`josStorer/get-current-time@v2.1.3` 和 `actions/upload-artifact@v7` 均以标签引用。

**影响：** 标签可被上游维护者移动；依赖账号或仓库遭到入侵时，后续发布构建可能执行未审查代码，访问工作流令牌并污染产物。

**建议：** 将 Action 固定到完整提交 SHA，并以注释记录对应版本；定期通过受控更新流程升级。

### F-04 — [P3] 插件版本解析会静默接受非数字格式

**位置：** `PulseBar/PluginUpdateHelper.cpp:14-34`；条目过滤位于同文件约 160 行。

**证据：** 每个点分段中的所有非数字字符都会被丢弃，之后只要整个版本字符串含任意数字，条目就可以进入商店。例如 `1.2beta3` 会按分段 `1.23` 参与版本比较，而不是作为格式错误拒绝。

**影响：** 清单拼写错误或异常版本可能被错误地排序，导致更新提示和本地版本判断不符合维护者意图。

**建议：** 按项目文档要求验证 `数字(.数字)*` 格式，拒绝空段与溢出段，并在解析失败时跳过该清单条目。

### F-05 — [P3] 一个测试脚本在模块导入时执行并退出，导致标准发现命令报错

**位置：** `tools/tests/test_display_text_repair.py:73-76`

**证据：** 原生测试构建和运行在模块顶层执行，文件末尾调用 `sys.exit(...)`。因此 `python -m unittest discover -s tools/tests -p 'test_*.py'` 导入该模块时收到 `SystemExit(0)`，将其报告为导入错误；该脚本直接运行则正常。

**影响：** 常规统一测试发现命令总是失败，自动化调用方无法单凭该命令区分真实测试失败与测试模块副作用。

**建议：** 将执行逻辑放到 `main()` 并置于 `if __name__ == '__main__':` 下；或拆成标准 `unittest.TestCase`，让发现器能安全导入。

## 十轮覆盖与验证
