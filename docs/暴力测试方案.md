# 暴力测试方案（PulseBar）

目标：用极端输入和异常操作验证程序不崩溃、不卡死、不写坏配置。
适用范围：本机 Release/Debug 构建（普通权限测试副本）。

## 1. 测试维度

| 维度 | 方法 | 判定 |
|---|---|---|
| 配置突变 | 在唯一测试目录写入负数、极大值、非法枚举、超长字符串和不存在路径 | 到达存活检查点；不把存活当作 UI/保存成功 |
| 启动退出循环 | 在唯一测试目录启动多个副本或重复启动 | 只检查测试副本数量和退出码；正常关闭另行验证 |
| 文件边界 | 损坏配置、历史、语言、背景图和插件文件 | 到达存活检查点；解析回退需有独立证据 |
| 资源采样 | 只查询测试 PID 的 GDI/USER/工作集/PrivateUsage | 稳态基线后观察平台期，不以一次增长判定泄漏 |
| 交互时序 | 需要真实窗口操作的设置/托盘/悬停场景 | 仅用官方桌面交互；未操作就标记未验证 |

新脚本每次在 `E:\AI\Zcode\tmp\traffic-monitor-ui-redesign\fuzzrun\` 下创建唯一目录，复制测试副本并替换互斥量和宿主窗口类名；不会使用正式程序的类名，也不会枚举全系统菜单窗口。到达检查点后的“存活”只代表进程尚未退出，不代表 UI 响应、配置保存或优雅退出成功。

旧的 `fuzz-commands.py` 和旧版菜单压力逻辑不再作为通过依据：它们使用旧窗口类名或全局菜单枚举，存在误碰正式实例/其他应用窗口的隔离缺陷。

## 4. 通过标准

- 所有用例进程存活，或按预期回退到默认值后存活
- 退出码不出现异常终止（0xC0000005 等）
- 配置读写必须由独立持久化测试或正常退出实测证明；存活检查本身不满足这一项
- 无残留测试副本进程

## 5. 已知限制

- 无法覆盖插件 DLL 内部崩溃（第三方代码）
- 无法覆盖真实多显示器/高 DPI 组合（需人工）
- 本轮不把随机命令洪水当作 UI 或功能验收

## 6. 首轮结果（2026-11-02）

### 发现并修复

| 用例 | 修复前 | 根因 | 修复 |
|---|---|---|---|
| `font_size = 99999` | 进程退出码 0x80000003 | 配置载入未校验字号，异常值进入字体创建 | 载入时限制在 5–72 |
| `digits_number = -1` | 进程退出码 0xE06D7363（C++ 异常） | 负值参与宽度计算 | 载入时限制在 3–10 |
| 静态检查 | 崩溃处理器复制路径长度用整串长度 | `memmove` 源偏移后长度未按剩余长度计算 | 改为按剩余长度并限长 |

同时补充了载入期校验：圆角 0–32、不透明度 1–100、流量提醒 1–32767、内存提醒 1–100、温度提醒 1–120。

### 修复后（旧测试副本，证据等级有限）

- 配置突变：24 / 24 到达存活检查点；未验证 UI 响应、保存和优雅退出。
- 命令洪水：旧脚本曾得到存活结果，但其隔离方式不合格，不再作为通过依据。
- 启动退出循环：旧脚本使用强制 `terminate`，不能称为正常启动/退出验证。

脚本位置：`tools/fuzz/fuzz-config.py`（已改为唯一类名/互斥量）、`tools/fuzz/fuzz-isolated.py`。

## 10. 长跑资源采样

最终采用 `tools/fuzz/resource-sampler.py`，只打开唯一隔离副本，不发窗口消息、不操作其他进程；修正了 Win32 函数原型并使用 `PROCESS_MEMORY_COUNTERS_EX.PrivateUsage`，不再把 `PagefileUsage` 误称为私有内存。

稳态采样 115.2 秒、24 个样本（启动后先等待 30 秒）：

| 指标 | 起始 | 结束 | 变化 |
|---|---:|---:|---:|
| GDI | 108 | 108 | 0 |
| USER | 54 | 54 | 0 |
| 工作集 | 64,512 KB | 64,936 KB | +424 KB |
| PrivateUsage | 34,028 KB | 34,196 KB | +168 KB |

这支持“该稳态窗口内没有观察到持续线性增长”，不等于一小时无泄漏。此前旧采样在首次打开设置附近出现 GDI 一次性增加，之后平台期；旧脚本动作是否真正执行不能作为严谨 UI 证据。

同样先等 30 秒再采样）：36 个样本、175.3 秒，GDI 108→109（+1）、USER 54→54（0）、
工作集 66,564→67,048 KB（+484 KB）、PrivateUsage 33,844→34,796 KB（+952 KB）。
样本跨度比上一轮长 60 秒、增量仍在同一量级，仍不足以宣称长期无泄漏。

## 11. 本轮源码复核与修复

## 13. 第二轮配置/预设/自启动复核（2026-11-02）

本轮聚焦“配置写盘、颜色预设、开机自启动读取”三条路径，全部为源码级确认 + 静态契约回归；配置写盘本身的原子性由第 12 节的持久化用例覆盖。

| 缺陷 | 触发条件 | 影响 | 修复 |
|---|---|---|---|
| 任务栏颜色预设保存被整体中断 | 任意一个预设的文字色与背景色全相同（`IsTaskBarStyleDataValid` 返回 false） | 该分支 `return;` 直接跳出 `SaveConfig()`，**其余所有预设的待写入改动和 `ini.Save()` 一起被丢弃**；`~CIniHelper()` 是空析构，不会兜底 | 单个预设无效只跳过它自身，循环结束始终 `ini.Save()`，并检查写入结果 |
| 预设日志编号错位 | 同上 | 日志打印 0-based 下标，用户看到“预设0”，而界面上是 1–4 | 改为 `i + 1` |
| `GetTemplateDir()` 对空缓冲区取 `back()` | `GetTempPath` 返回 0（临时目录不可用/环境损坏） | 对空 `wstring` 调用 `back()` 是未定义行为 | 缓冲区零初始化，失败或空串直接返回空串 |
| 空临时目录串被当成“命中 Temp 目录” | 上一条返回空串时 | `find(L"")` 对任意路径恒返回 0，于是被误判为“运行在 Temp 目录下”，**便携模式被强制切换成 AppData 模式** | 先用 `!temp_dir.empty()` 守卫再匹配 |
| 自启动读取未初始化缓冲区 + 空值取 `front()/back()` | 注册表值不存在但 `QueryStringValue` 异常成功、或值为空串 | 读未初始化栈内存；对空串取首尾字符是未定义行为 | 缓冲区 `{}` 零初始化；构造 `registered_path` 后再判断非空 |
| 带引号的历史自启动项被判为“未启用” | 旧版本把路径连引号一起写入 `HKCU\...\Run` | 注册表原始值 `"...\PulseBar.exe"` 与 `m_module_path_reg` 永不相等，设置页显示“未开机自启”，用户再点一次会重复写入 | 去引号后再比较，并回填给调用方 |
| `SplitStringList` 对单字符元素 `substr(1)` 后 `pop_back()` | 配置值损坏成只有一个 `"` | 空串 `pop_back()` 是未定义行为 | 首项按长度分支处理，末项先判空再 `pop_back()` |
| 多字符 `_StringSplit` 传入空分隔符 | 配置/插件字符串退化 | 空分隔符使 `find` 每次返回 0，循环按字符数空转并产出一串空项 | 空分隔符直接退化为不拆分 |
| `WriteLog` 未校验空路径/空文本 | 配置目录尚未确定时写日志（如早期失败路径） | 用空路径构造 `ofstream` 必然失败，日志静默丢失且掩盖真实错误 | 空指针/空路径直接返回 |
| 硬件初始化线程持锁弹模态框 | OpenHardwareMonitor 初始化抛异常（`CreateInstance` 返回 nullptr） | 该线程持有 `m_minitor_lib_critical` 并调用 `AfxMessageBox`；`GeneralSettingsDlg` 打开设置页时要在 UI 线程拿同一把锁，于是**设置页永久卡死**，直到有人关掉一个可能根本看不见的弹窗；`.NET` 异常文本还可能为空 | 改为写日志（空文本时退回通用硬件错误文案），与采样线程的硬件错误处理一致 |

## 14. 第三轮：空选中下拉框与配置枚举越界（2026-11-02）

本轮全部缺陷属同一族：**值来自 `config.ini` 或来自一个可能没有选中项的下拉框，写入前没有任何范围校验**。它们不会崩溃，只会让界面看起来“没有设置”或静默显示错误的数据，因此比崩溃更难被用户识别。

### 14.1 空选中下拉框（`GetCurSel()` 返回 -1）

`CBS_DROPDOWNLIST` 在没有任何选中项时 `GetCurSel()` 返回 `-1`、`GetWindowText()` 返回空串、`GetLBText(-1, …)` 什么也不写入。把这类值直接写进草稿或枚举，会持久化成垃圾。

| 位置 | 原行为 | 影响 | 修复 |
|---|---|---|---|
| `CTaskBarSettingsDlg::OnCbnSelchangeUnitCombo` | 无守卫 | `-1` 转成 `SpeedUnit` 越界枚举 | 未选中直接 `return` |
| `CTaskBarSettingsDlg::OnCbnSelchangeMemoryDisplayCombo` | 无守卫 | `-1` 转成 `MemoryDisplay` 越界枚举 | 同上 |
| `CTaskBarSettingsDlg::OnCbnSelchangeNetSpeedFigureMaxValueUnitCombo` | 无守卫 | 写入 `-1` | 同上 |
| `CTaskBarSettingsDlg::OnCbnSelchangeDigitNumberCombo` | 无守卫 | `-1 + 3 = 2`，位数变成 2 位 | 同上 |
| `CGeneralSettingsDlg::OnCbnSelchangeSelectHardDiskCombo` | 无守卫 | 硬盘名被写成空串 | 同上 |

## 15. 第四轮：硬件监控锁与启动/设置延迟（2026-11-03）

起因是"设置界面加载慢"。追下去发现同一个锁（`m_minitor_lib_critical`）被三个线程以互相冲突的方式使用，修复过程中又暴露出一个我自己引入的启动回归。

### 15.1 根因：UI 线程在采样/初始化锁上等待

`m_minitor_lib_critical` 有两类持有者：初始化线程跨 .NET `CreateInstance()`（冷启动数秒）持锁；采样线程跨 `GetHardwareInfo()` 与每次温度读取持锁。设置页原本为了拿 CPU/硬盘温度项名称，直接去抢这把锁——于是"打开设置"的耗时等于"等初始化/等一次采样"。

修复改为快照读：`m_temperature_names_critical` 保护 `m_cpu_temperature_names` / `m_hdd_temperature_names`，采样线程在持有硬件锁时刷新快照，UI 线程只拿快照锁。锁序固定为 `m_minitor_lib_critical` → `m_temperature_names_critical`，UI 线程只拿后者，不成环。

### 15.2 快照必须在扫描之后写（此前一段的回归）

温度项名称只在 `GetHardwareInfo()` 里填充，`CreateInstance()` 只做 `MonitorGlobal::Init()`（`gcnew UpdateVisitor()`、`gcnew Computer()`、`computer->Open()`）。若在 `CreateInstance()` 之后立刻写快照，抓到的是空 vector，冷启动后马上打开设置页会看到空的 CPU/硬盘下拉框。修复：初始化线程先扫一次硬件，再 `RefreshTemperatureNameSnapshotLocked()`。设置页在两条向量都为空时挂一个 300 ms 的 `TIMER_TEMP_NAMES` 轮询（有上限、跳过展开中的下拉框），等后台扫描落地。

### 15.3 `m_pMonitor` 的三处 TOCTOU / 数据竞争

`m_pMonitor` 是 `std::shared_ptr`，所有写入都在 `m_minitor_lib_critical` 内（初始化线程赋值、`ApplySettings` 的 `reset()`）。三处读取却在锁外求值，既是形式上的数据竞争，也留下"判空→进锁→解引用"之间的窗口：

| 位置 | 原写法 | 后果 |
|---|---|---|
| `CPulseBarDlg::DoMonitorAcquisition` | `if (IsTemperatureNeeded() && theApp.m_pMonitor != nullptr)` 在 `CSingleLock` 之前 | 用户在两步之间关闭硬件监控，采样线程随后解引用空指针；该线程温度读取没有异常保护 |
| `CPulseBarApp::UpdateOpenHardwareMonitorEnableState` | `CSingleLock` 在 `if (m_pMonitor != nullptr)` 之后 | 同上，发生在 UI 线程点"确定"时 |
| `CPulseBarDlg::ApplySettings` | `else if (theApp.m_pMonitor != nullptr)`，完全未持锁 | 与初始化线程的赋值竞争 |

修复：判空全部移进锁内。`ApplySettings` 改为在作用域锁内取一次 `bool monitor_ready`，再按该局部值分派。

### 15.4 修复引入的启动回归与最终形态

把判空移进锁内后，采样线程变成"每个采样周期无条件抢硬件锁"。冷启动时初始化线程正跨 .NET 加载持锁数秒，任务栏整段停止刷新——这比原来的问题更明显。

最终形态是"原子状态做锁外快速跳过，指针判空留在锁内"：

- `std::atomic<int> m_monitor_state`，三态 `MONITOR_NONE / MONITOR_INITIALIZING / MONITOR_READY`，读端通过 `IsHardwareMonitorReady()` / `IsHardwareMonitorInitializing()` 访问。
- 采样线程：`IsTemperatureNeeded() && theApp.IsHardwareMonitorReady()` 为假就直接跳过，不碰锁；为真才进锁，锁内仍做 `m_pMonitor != nullptr` 判空。
- 初始化线程：`CreateInstance()` 后按结果置 `READY` 或 `NONE`，置位在长扫描之前，避免首扫期间任务栏冻住。
- 关闭硬件监控：在锁内先 `reset()` 再退回 `MONITOR_NONE`（顺序保证采样线程不会漏读活着的实例）。
- `ApplySettings` 在初始化进行中直接交给已在跑的初始化线程（它收尾时按已提交的 `m_general_data` 设置启用项），不再等锁。
- `InitOpenHardwareLibInThread` 用 `compare_exchange_strong(NONE → INITIALIZING)` 抢占，避免初始化中点"确定"再起第二个线程、白付一次 .NET 加载。

### 15.7 第六轮：温度项下拉框的填充结果（2026-11-03）

对"设置页第 3 页（网络与采集）的 CPU/硬盘温度下拉框是否填对"做了逐项实测。结论分两部分：
CPU 侧正确，硬盘侧**在隔离环境里无法验证**（不是产品缺陷，是测试副本的权限与分发 exe 不同）。

**CPU 下拉框：`items=36, cursel=34` 是正确的，不是缺陷**

`probe-combodump.py`（`hardware_monitor_item = 5`，打开设置 → 切到第 3 页 → 等 3 s）输出：

```
after 3s cpu: hwnd=48892746 matches=1 items=36 cursel=34
  cursel text = 'Core Average'
  [0] '平均温度'   [1] 'CPU Core #1' ... [33] 'CPU Package' [34] 'Core Average' [35] 'Core Max'
```

36 项 = `CCommon::LoadText(IDS_AVREAGE_TEMPERATURE)` + 35 个 LHM 温度传感器名。
`cursel=34` 是 `FindString(-1, L"Core Average")` 命中默认值 `general/cpu_core_name` 的结果，
不是"前缀误匹配"。`matches=1` 确认页面内没有第二个控件占用 id `1134`。
从 `items=1`（只有"平均温度"）涨到 36 项约 3 s，是后台初始化线程跑完
`CreateInstance` + 首次 `GetHardwareInfo()` 的时间，与第 15.5 节记录的快照/重试设计一致。

**硬盘下拉框：`items=0, cursel=-1` 属环境限制，未验证，不得当作"工作正常"**

同一探针的硬盘侧输出 `matches=1 items=0 cursel=-1`——id `1129` 只有一个控件，不存在 id 串扰，
就是列表真的空。追下去的原因链：

1. `hardware_monitor_item = 5`（CPU|HDD）使 `PulseBarDlg.cpp:2148` 的 PDH 分支不成立
   （`!IsHardwareEnable(HI_HDD)` 为假），`m_get_disk_usage_by_pdh` 保持 `false`，
   于是 `FillTemperatureNameCombos()` 走 `!IsGetDiskUsageByPdh()` 分支，**只用 LHM 的 Storage 名**，
   而 PDH 那套 `"0 c: d: e:"` 实例名不会出现。
2. LHM 的 Storage 名来自 SMART 枚举，需要管理员权限：
   非提权下 `\\.\PhysicalDrive0` 句柄本身能打开，但 `IOCTL_SMART_GET_VERSION`(0x074080)
   返回 `err=6`（`ERROR_INVALID_HANDLE`）。
3. 独立复核（`tmp/hwprobe/lhm-enumerate.ps1`，只开 CPU+Storage）：非提权下
   `hardware count: 1`，只有 `[Cpu] 13th Gen Intel Core i7-13700KF`，**没有任何 Storage 设备**；
   同期 WMI 能列出 4 块物理盘（TOSHIBA MG09ACA18TE / ZHITAI TiPlus7100 2TB / 2 个 USB），
   `MSFT_PhysicalDisk` 非提权也可枚举。说明盘在、LHM 看不到，差别就是权限。
4. 而 `tools/fuzz/isolated_runner.py` 的 `patch_copy()` 会把清单改成
   `requestedExecutionLevel level="asInvoker"`，**所有隔离测试都是非提权的**；
   分发的 `src/Bin/x64/Release/PulseBar.exe` 内嵌的是

### 15.8 第七轮：连接详情窗口与运行时间算法（2026-11-03）

本轮审计 `NetworkInfoDlg.cpp`（连接详情窗口）与它唯一依赖的时间工具
`CCommon::CompareSystemTime`。分三项记录，并明确区分"已复现/已修复/仅静态候选"。

**（1）已复现并已修复：跨天/时钟回拨时"程序已运行时间"算错**

`CompareSystemTime` 原来只做时分秒相减：

```cpp
short hour = a.wHour - b.wHour;   // 忽略日期
if (second < 0) { second += 60; minute--; }
if (minute < 0) { minute += 60; hour--; }
if (hour < 0) { hour += 24; }     // 负值一律 +24 兜底
```

后果是运行时间按 24 小时取模，且时钟往回调时给出假值。用同一组算式的算术副本对照
（`old` = 原实现，`new` = 新实现，参数为「当前时间, 启动时间」）：

| 场景 | 原实现 | 新实现 |
|---|---|---|
| 跨天 20 分钟（23:50 启动，次日 00:10） | `0小时20分0秒` | `0小时20分0秒` |
| 跨两天 48 小时 | **`0小时0分0秒`** | `48小时0分0秒` |
| 系统时钟往回调 1 小时 | **`23小时0分0秒`** | `0小时0分0秒` |
| 同日 30 秒 | `0小时0分30秒` | `0小时0分30秒` |
| 同日 23h59m58s | `23小时59分58秒` | `23小时59分58秒` |

修复：`Common.cpp` 的 `CompareSystemTime` 改用 `SystemTimeToFileTime` 把两个时刻转成
100ns 计数再相减，秒数总差值再拆成时分秒；当前时间早于启动时间（时钟回拨）时按 0 处理；
`SystemTimeToFileTime` 失败时退回原时分秒算法，保持原有调用契约（只被
`NetworkInfoDlg.cpp:195` 使用，`GetProgramElapsedTime` 每秒刷新一次）。

### 15.9 第八轮：插件模块的边界与空指针（2026-11-03）

插件是唯一一处"外部代码按 ABI 契约直接进入进程"的输入面。`PluginInterface.h` 的注释只写了
`GetItem()` 在"其他情况"返回空指针，对返回值的其它字段没有任何强制；插件加载发生在主窗口
创建**之前**（`CPulseBarApp::InitInstance` → `m_plugins.LoadPlugins()`），所以这里的崩溃
表现为"双击后没有任何窗口出现"，用户侧完全看不到可诊断的信息。

本轮用一个自己写的恶意插件（`tmp/probe-plugin/HostilePlugin.cpp`，两个变体）验证：

- `HostilePlugin.dll`：`GetItem()` **永不返回空指针**，每次返回同一个无 ID 的项目。
- `HostilePluginBounded.dll`：`GetItem(0)` 返回一个 `GetItemName()`/`GetItemId()` 都为空的
  项目，`GetItem(1)` 起返回空指针；`GetTooltipInfo()` 返回空指针；`GetCommandCount()` 返回 0。

两个变体都用 `_wfopen_s(..., L"a, ccs=UTF-8")` 写自己的日志，因此插件日志是带 BOM 的 UTF-8
（读用 `utf-8-sig`）；而宿主 `CCommon::WriteLog` 经 `UnicodeToStr` 落盘，`error.log` 是
**ANSI(cp936)**。探针必须两种编码各试一次，用一种解码另一种只会得到乱码。

> **复现前提（每一条记录都适用）**：隔离副本的清单被 `tools/fuzz/isolated_runner.py::patch_copy()`
> 从 `requestedExecutionLevel level="requireAdministrator"` 改写为 `level="asInvoker"`，
> 因此**所有隔离运行都是非提权的**，与用户实际运行的分发产物（提权）在权限上下文上不同。
> 本轮的崩溃与内存曲线均在这一非提权上下文下取得；结论不依赖提权与否，但不应把
> "非提权下通过"读成"提权下同样验证过"。

### 15.10 第九轮：悬停面板的 DPI 布局不一致（2026-11-03）

这一轮的问题**只在非 100% 缩放上出现**，而本机正好是 125%（120 dpi），因此它是用户日常看到的
缺陷，却不会在任何 96 dpi 的机器上暴露。

**（1）P17 已复现并已修复：窗口高度按 dpi 缩放，绘制纵轴不缩放 → 面板底部空一条**

`CSpeedGraphTip` 的纵向几何有两份独立算式：

- `CalcWindowHeight()` 把整条 155px 的堆叠按 dpi 缩放（`HEADER_H`/`VALUE_H`/`NET_CHART_H`… 全部乘 `dpi/96`）；
- `Draw()` 却用**未缩放**的常量算纵轴：`const int y_value = HEADER_H + 2;`、
  `y_net = y_value + VALUE_H + 1 + VALUE_H2 + 2;`、`y_cpu = y_net + NET_CHART_H + CHART_GAP;`，
  两张曲线图的高度也直接取 `NET_CHART_H`/`CPU_CHART_H`；
- 而左右内边距（`PAD * dpi / 96`）是缩放的。

在 96 dpi 下两套算式都等于 155，**逐像素相同**，所以这个分歧在开发机上完全看不出来。
本机 120 dpi 实测（隔离副本，非提权，见下方前提）：

```
修复后  B1 panel_rect=(1603,1195,2078,1385) 475x190
        B2 visible=True panel_dpi=120
        B3 expected=475x190 match=True

        B7 content_bottom_equals_window_h=True blank=0
```

即窗口比实际画出来的内容高 **35–38 px**，底部是一条纯背景色的空带。按同一算式推算其它缩放：

| 面板 dpi（缩放） | 窗口高度 | 旧绘制的固定内容底边 | 底部空带 |
|---|---|---|---|
| 96（100%） | 155 | 155 | **0**（所以开发机上不可见） |
| 120（125%） | 190 | 155 | **35** |
| 144（150%） | 232 | 155 | **77** |
| 168（175%） | 267 | 155 | **112** |
| 192（200%） | 310 | 155 | **155** |

修复：把纵向布局收敛成**唯一一份**算式。新增 `PanelLayout` 结构与 `CalcLayout(int dpi)`，
`CalcWindowHeight()` 直接 `return CalcLayout(dpi).bottom;`，`Draw()` 的
`y_value`/`y_net`/`y_cpu` 与两张图的高度全部取自同一个 `layout`。这样"窗口高度 == 内容底边"
变成结构性的等式，而不是两处算式碰巧相等。96 dpi 下的输出与修复前逐值相同
（155 / 18 / 20 / 51 / 105），所以 100% 缩放的观感没有任何变化。

**（2）同轮修复的两个连带缺陷**

- **图钉热区不随 dpi 缩放**：`PinRect` 原本写死 `CRect(client_w - 34, 0, client_w - 6, HEADER_H)`，
  是 28×18 的固定矩形；而头行高度是 `S(HEADER_H, dpi)`。120 dpi 下头行高 22、热区仍只有 18，
  上半部分点不到；144 dpi 下头行 27、热区 18，热区甚至盖不到图钉的视觉中心。已改为
  `S(34, dpi)` / `S(6, dpi)` / `S(HEADER_H, dpi)`（120 dpi 下热区 35×22）。
- **放置间距与悬停桥接间距不同源**：`Show()` 里面板距任务栏 `PANEL_GAP` 未缩放（恒为 4），
  而 `IsCursorInHoverRegion()` 里判定"光标在面板与任务栏之间的桥接区"时也用了未缩放的间隙。
  高 dpi 下若两处再各自改动一处，就会出现 1–2 px 的死区：光标移进空隙时面板判定为"离开"并消失，
  用户看到面板闪烁。已统一为 `S(PANEL_GAP, m_dpi)`，两处同源。

**（3）探针本身的两个坑（记录以免误判）**

- **DPI 虚拟化**：探针若声明为 DPI-unaware，`GetWindowRect` 返回的是**虚拟化**坐标
  （`真实值 × 感知dpi / 面板dpi`）。本机面板在 120 dpi，unaware 进程读到 `380x152`、
  `GetDpiForSystem()=96`，正好是 `475×0.8`、`190×0.8`。第一轮因此误报"380x152 与预期 155 不符"——
  错的不是产品而是探针。修正方式是显式 `SetProcessDpiAwareness(2)` +
  `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`，并用 `GetDpiForWindow(panel)`
  现场取面板真实 dpi 再算期望值。**结论：任何几何断言都必须先确认探针自身 dpi 感知级别。**
- **多任务栏**：多显示器下 `Shell_TrayWnd` 只是主屏那块，副屏是 `Shell_SecondaryTrayWnd`；
  且宿主可能嵌在**任意**一块上。只枚举 `Shell_TrayWnd` 的子窗口会拿到别块任务栏的矩形，
  于是"间距 658、未居中"这类假失败。修正为枚举所有 `Shell_TrayWnd`/`Shell_SecondaryTrayWnd`
  的子窗口，逐个投递 `WM_MOUSEMOVE`，再取"面板实际贴着的那块"（最小间距）做断言。
  修正后 `B4 gap_above_taskbar=5 (expected 5)`、`B5 panel_centered_on_cursor=True`。

### 15.11 第十轮：悬停面板整块跑出显示器（2026-11-03）

15.10 修的是面板**内部**的几何；这一轮修的是面板**外部**的放置。两者都在 `CSpeedGraphTip::Show()`，
但触发条件不同：这一轮不需要非 100% 缩放，只需要用户动过一个合法设置。

**（1）P18 已复现并已修复：`Show()` 不夹紧显示器边界，任务栏被偏移后整块面板落到屏幕外**

旧 `Show()` 的放置只有三条规则：

```cpp
int x = cursor_pos.x - w / 2;                 // 以光标居中,没有任何水平边界
int y = taskbar_wnd_rect.top - h - gap;       // 优先贴任务栏上方
if (y < 0)                                     // 放不下就翻到下方
    y = taskbar_wnd_rect.bottom + gap;
```

两个问题叠在一起：

1. **水平方向完全不夹紧。** 面板以光标为轴居中，光标靠右时光标仍在任务栏内，但面板右半截
   可以伸出显示器。任务栏窗口本身在屏幕内时，面板宽度 475px、光标在任务栏中心，
   这个溢出还能被"任务栏中心离屏幕右缘足够远"掩盖；任务栏一旦被推到屏幕边缘就必然整块溢出。
2. **垂直翻转判据用的是虚拟桌面原点 `y < 0`，不是所属显示器的上边缘。** 本机就存在负原点显示器
   （枚举结果为 `\\.\DISPLAY1 = (-2160,-787,0,3053)`，竖屏副屏在 x<0、y<0 区域），
   在那块屏上 `y` 天然为负，翻转判据会立刻误触发——不管上方其实有没有空间。

而"任务栏被推到屏幕边缘"是**用户可配置的**，不是异常状态：

- `window_offset_left` 在 `CommonData.cpp:485-491` 被校验为 **±800 逻辑像素**，
  `Win11TaskbarSettingDlg.cpp:84` 的 `SetRange(-800, 800)` 与之对应（`window_offset_top` 是 ±20）；
- `CWin11TaskbarDlg::AdjustTaskbarWndPos` 在 `Win11TaskbarDlg.cpp:67` 施加这个偏移，
  而紧跟其后的**屏幕边界夹紧被整段注释掉了**（同文件 68-72 行）。
  也就是说这个偏移可以把任务栏窗口推到显示器之外，没有任何东西拦它。

本机 120 dpi、主屏 `(0,0,2560,1440)`、`window_offset_left = 800`（物理 +1000）实测
（隔离副本、非提权、探针 DPI-aware，见 15.10 的三个前提）：

```

        panel=(2603,1195,3078,1385) 475x190 dpi=120 gap=5
        monitor=(0,0,2560,1440) overflow_right=518 fully_inside_monitor=False
```

面板右缘 3078 对显示器右缘 2560，**溢出 518 px**，整个面板的右侧一半在屏幕外；
而 `offset=0`（C1）与 `offset=-800`（C3）都完全在屏内——所以这个缺陷只在用户把
"任务栏窗口水平偏移"调大后才出现，属于"用户改了一个合法设置就坏"的类型。

**修复：**

- 新增匿名命名空间 helper `GetTaskbarMonitorRect()`：用
  `MonitorFromRect(taskbar_rect, MONITOR_DEFAULTTONEAREST)` + `GetMonitorInfo` 取
  **任务栏窗口所属那块显示器**的 `rcMonitor`。用 `MONITOR_DEFAULTTONEAREST` 而不是
  `MonitorFromWindow` 的默认行为，是为了在任务栏已被推到屏幕外时仍能拿到"最近的那块屏"
  作为夹紧边界，而不是拿到 `nullptr` 后放弃夹紧。查不到显示器信息时退化为整个虚拟桌面
  （`SM_XVIRTUALSCREEN` 等四个 metric），即回到旧行为，不留未初始化矩形。
- `Show()` 先取边界，再对**两个轴**都夹紧，并且每个轴夹两次：

```cpp
int x = cursor_pos.x - w / 2;
if (x + w > monitor_rect.right)  x = monitor_rect.right - w;
if (x < monitor_rect.left)       x = monitor_rect.left;   // 显示器比面板还窄时贴左边

int y = taskbar_wnd_rect.top - h - gap;
if (y < monitor_rect.top)        y = taskbar_wnd_rect.bottom + gap;  // 上方放不下才翻到下方
if (y + h > monitor_rect.bottom) y = monitor_rect.bottom - h;
if (y < monitor_rect.top)        y = monitor_rect.top;    // 显示器比面板还矮时贴顶边
```

  第二次回夹是必要的：翻转分支（`taskbar.bottom + gap`）本身也可能超出下边缘
  （任务栏贴着屏幕底部时几乎必然如此），只夹一次就会把面板翻到屏幕下方。
  同时把缩放间隙提升为 `const int gap = S(PANEL_GAP, m_dpi);`，上下两个分支共用同一个值
  （15.10 的"两分支不得各自算一遍"约束继续成立，契约已按此改写）。

### 15.12 第十轮续：悬停面板在自定义主题下用了写死配色（2026-11-03）

**症状**：把任务栏主题切到"自定义"后，悬停弹出的速度图面板仍是深灰色，与紧贴其上的任务栏配色不一致。

**根因**：`CSpeedGraphTip::Draw()` 用 `FindTaskbarTheme(theApp.m_taskbar_data.tb_theme)` 取主题，
但 `AllTaskbarThemes[]`（`CommonData.h:275-285`）只收录 id **1..8**，而 `tb_theme == -1`
是**自定义主题哨兵**（`PulseBar.cpp:270-271` 把 `tb_theme` 夹在 `-1..7`）。
`FindTaskbarTheme`（`CommonData.cpp:14-22`）线性搜表，对 -1 返回 `nullptr`，
于是 `Draw()` 走 `theme != nullptr ? ... : RGB(32,32,36)` 的写死回退分支，
`PanelLabelColor` / `PanelValueColor` / `PanelAccentColor` 三个 helper 同样收到 `nullptr`，
**四种颜色一起退回默认值**。

对照组证明这不是"面板根本不支持主题"：同一份代码在 `tb_theme == 1`（内置"圆角深色"）
下正确取到 `32,34,40`。而任务栏本体 `CTaskBarDlg::DrawDisplayItem`（`TaskBarDlg.cpp:245`）
和 `SetTextFont`（`827`）用的是 `GetActiveTaskbarTheme()`，
`CTaskBarSettingsDlg::OnDrawItem`（`TaskBarSettingsDlg.cpp:1464`）对 `tb_theme == -1`
显式分支——即**面板与它所属的任务栏在同一份配置下取到了不同配色**。

**隔离复现**（`tmp/probe-speedtip-theme.py`，DIB 抓 `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)`
后按 BGRA 取像素，不依赖窗口是否被遮挡；测试副本来自本轮 Debug `b8a2a0ee…`）：

```
T1 theme=1  custom=False panel_size=(475,190) bg_pixel=(30,32,38)  expected=None        match=True
T2 theme=-1 custom=True  panel_size=(475,190) bg_pixel=(30,30,34)  expected=(64,128,192) match=False
```

- `T1` 的 `30,32,38` = 主题 1 的 `32,34,40` 叠 242/255 透明度 → 主题通路本身是通的。
- `T2` 的 `30,30,34` = **写死回退值 `32,32,36`** 叠同一透明度 → 自定义色 `64,128,192`
  完全没有到达面板。探针把自定义调色板刻意设成 `custom_bg = 0x00C08040`
  （RGB 64,128,192）、`custom_label` 纯绿、`custom_value` 纯红、`custom_accent` 品红，
  保证不会与任何回退值撞车。

**修复**：`Draw()` 改用 `GetActiveTaskbarTheme()`（`CommonData.cpp:25-43`），
它在 `tb_theme == -1` 时合成一个 `id = -1`、`bg_r/g/b` 取自 `custom_bg`、
`label/value/accent/style/value_bold` 取自 `custom_*` 的静态条目，与任务栏本体同源。
`Draw()` 内仍保留 `theme != nullptr` 判断——`tb_theme == 0`（经典主题，无面板）
在表里同样查不到，此时退回写死深灰是**既有且正确的行为**，不在本次修复范围内。

### 15.13 第十轮续二：`SpeedGraphTip.cpp` 剩余三个候选的裁决（2026-11-03）

前两节修完后，`SpeedGraphTip.cpp` 还剩三处可疑点。逐条裁决，**其中两处不是缺陷**，
一处是文档缺陷，一处做了零成本加固。

#### A. `DrawChartLegend` 的 `int x = chart.right - total;` 未夹紧 —— 加固，不是缺陷

两项图例文案是**写死的字面量**：`↓下载`/`↑上传`（第 470 行）、`CPU`/`GPU`（第 521 行），
各 3 个字符。按 `total = Σ(sw + gap + text + gap)` 与 `chart.right = S(380) - S(4)` 算：

| dpi | 图例 | chart.right | total | x |
|---|---|---|---|---|
| 96 | ↓下载/↑上传 | 376 | 94 | **282** |
| 96 | CPU/GPU | 376 | 72 | **304** |
| 120 | ↓下载/↑上传 | 470 | 114 | 356 |
| 144 | ↓下载/↑上传 | 564 | 136 | 428 |
| 192 | ↓下载/↑上传 | 752 | 188 | 564 |

要让 `x` 变负，96dpi 下每项需 ≥16 个 CJK 字（20 字时才到 `x = -24`）。
**当前不可达**。仍加了 `if (x < chart.left) x = chart.left;` 兜底：
未来改文案或缩窄面板时图例不会画出面板左缘。新增契约
`test_chart_legend_is_clamped_to_the_chart_left_edge`。

#### B. `AddSample` 的取整 —— 行为可接受，注释与代码不符是真缺陷

代码：
```cpp
m_max_speed = max((unsigned long long)(max_v * 1.25), (unsigned long long)1024);
m_max_speed = ((m_max_speed / 1024) + 1) * 1024;
```
第二行是"严格大于"语义：`x` 恰为 1024 整数倍时结果多跳一个 1024（1024 → 2048，
2048 → 3072）。**Y 轴上界多 1KB 对 50px 高的曲线区意味着曲线矮约 2% 以内，视觉不可辨，
且方向是"更保守"（峰值更矮），不是缺陷**。副作用：注释写"最小 1KB 避免除零"，
实际最小值是 **2048**。

真正的问题是**两行相邻注释互相矛盾**：原第 160 行写"向上取整到 **10KB** 的倍数，
且不低于峰值的 **1.2 倍**"，原第 168 行写"峰值的 **1.25 倍**，向上取整到 **1KB** 的倍数"。
代码是 1.25 倍 + 1KB。同一段连续两行注释给出四个互斥数字，读代码的人必然被误导。

**修复**：合并成一条准确注释（删掉错误的那条），写明"1.25 倍 / 1KB 倍数 /
下限 1024 经 +1 步进后为 2048"。新增契约
`test_add_sample_rounding_comment_matches_the_code`——要求出现 `1.25` 与 `1KB`、
**禁止**出现 `10KB` 与 `1.2 倍`、并锁住 `((m_max_speed / 1024) + 1) * 1024` 这一算式。

#### C. `CreateWindowIfNeeded` 忽略 `RegisterClassEx` / `CreateWindowEx` 返回值 —— 不是缺陷

- `RegisterClassEx` 返回 0 的常见原因是 `ERROR_CLASS_ALREADY_EXISTS`（重复注册同名类），
  此时窗口仍可创建，忽略返回值无害；其它失败原因下 `CreateWindowEx` 也会失败，
  由下一条兜住。
- `CreateWindowEx` 失败时 `m_hWnd` 保持 `nullptr`，而唯一调用方 `Show()`
  第 207 行是 `if (m_hWnd == nullptr || !IsWindow(m_hWnd)) return;`，
  **已在下游拦截**，不会对空窗口调用 `SetWindowPos`/`ShowWindow`。
- `WM_NCCREATE` 的 `self` 赋值发生在 `CreateWindowEx` 内部，失败时不会走到绘制。

**结论：有下游防护，不改。** 保留 `m_hWnd{ nullptr }` 初值作为失败信号即可。

### 15.14 第十一轮：设置页切页残影与最终产物全量回归（2026-11-03）

**症状**：在"选项设置"里切换左侧导航时，新页面的分组框内部会透出**上一页的文字和边框**。
表现为分组框标题下方浮着一行旧页的标签，或者旧页的"排列与格式"字样出现在新页的"硬件监控"框里。
截图见 `tmp/shots-vis9/1-ghosted.png`（切到"网络与采集"后，框内残留"排列与格式"、
"水平排列"、"选择监控的硬盘"等上一页内容）。

**根因**：两个子页 `CTaskBarSettingsDlg`（页 0–2）与 `CGeneralSettingsDlg`（页 3–5）
是**两个独立的 `#32770` 子窗口，共用同一块矩形**，靠 `SW_HIDE` / `SW_SHOW` 切换。
子页模板声明了 `WS_CLIPCHILDREN`（见 `PulseBar.rc` 的 `IDD_TASKBAR_SETTINGS_DIALOG` /
`IDD_GENERAL_SETTINGS_DIALOG` 的 `STYLE` 行），但**没有 `WS_CLIPSIBLINGS`**。

`WS_CLIPCHILDREN` 只让父窗口在擦除自身时跳过子窗口覆盖的区域，而**不**让父窗口跳过
"另一个兄弟子窗口"覆盖的区域——那是 `WS_CLIPSIBLINGS` 的职责。所以：

1. 旧页可见时，父窗口（`COptionsDlg`）的 `WM_ERASEBKGND` 被 `WS_CLIPCHILDREN` 限制在子页矩形**之外**，
   子页矩形内的像素全部由子页自己画。
2. 切页时 `ShowWindow(SW_HIDE)` 旧页、`ShowWindow(SW_SHOW)` 新页。旧页隐藏后，那块区域变成
   "父窗口可见但从未被擦除"的死区；新页显示时只画自己的客户区，
   **分组框（`BUTTON` 控件）内部是空心的，不填背景**，于是父窗口表面残留的旧页像素就从框里透出来。
3. 只有"父窗口在**两个子页都隐藏**时同步擦除这块矩形"才能清掉残影——这也是为什么单纯
   `Invalidate` 新页无效：新页盖在上面，父窗口依旧被 `WS_CLIPCHILDREN` 挡住。

**机制验证（`tmp/probe-vis9.py`，四步对照，图存 `tmp/shots-vis9/`）**：

| 步骤 | 操作 | 截图 | 结果 |
|---|---|---|---|
| 1 | 切到页 3 | `1-ghosted.png` | 残影出现（旧页文字在分组框内） |
| 2 | 隐藏页 → 父窗口擦除该矩形 | `2-erased.png` | 页面区变成干净底色，**残影消失** |
| 3 | 重新显示页 | `3-reshow.png` | 页面完整重绘，**残影未回来** |
| 4 | 整棵窗口树 `RDW_INVALIDATE\|RDW_ERASE\|RDW_ALLCHILDREN\|RDW_UPDATENOW` | `4-fullredraw.png` | 与步骤 3 相同，说明步骤 2 的擦除已足够 |

步骤 2 是决定性证据：**只擦父窗口、不碰子页内容**，残影就消失了 → 残影的像素确实在父窗口表面，
不在子页表面。这排除了"子页没重绘干净"的替代解释。

**修复**（`src/PulseBar/OptionsDlg.cpp`，`COptionsDlg::SelectPage`）：
在真正换页时（`m_shown_section` 与目标分区不同）先隐藏两页，再让父窗口
`RedrawWindow(page_rect, nullptr, RDW_INVALIDATE | RDW_ERASE | RDW_UPDATENOW)` 同步擦除，
然后 `LayoutPages()`、显示目标页、对目标页整棵子树
`RedrawWindow(nullptr, nullptr, RDW_INVALIDATE | RDW_ERASE | RDW_ALLCHILDREN | RDW_UPDATENOW)`。

两个细节：

- **只在真正换页时做**。同一页重复进入（含首次打开）走廉价路径，不付这套擦除成本。
  `m_shown_section` 初值 `-1` 保证首次打开不会误判为"换页"。
- **擦除矩形取自 `target->GetWindowRect()` 再 `ScreenToClient`**，而不是从布局常量重算：
  子页的实际矩形由 `LayoutPages()` 决定，用实测矩形可以避免常量与实现漂移。

`CTabDlg::RepaintPageSwitch()`（`TabDlg.cpp:124-142`）保持原有形态（隐藏→父窗口
`Invalidate`+`UpdateWindow`→显示→`UpdateWindow`），因为它在子页**自身**切换分区时被调用，
父窗口此时已经知道要擦除；两处职责不重叠。

#### 15.18 设置页打开速度优化（2026-11-04）

背景：用户反馈设置页打开仍慢。15.16 的首屏修复消除了白屏，但隔离测试显示每次打开仍有
约 280–310ms 的创建成本。本轮先对 Create 路径做分段测量定位成本分布，再按数据实施分区
延迟初始化，以 104 项原生断言与双配置回归验证，最后撤除全部插桩并保留干净源码。

##### 15.18.1 分段测量（临时插桩，测量后撤除）

对 Create 路径加 `PULSEBAR_OPTIONS_PERF` 编译开关下的 QPC 分段计时，覆盖父对话框模板与
遍历、页模板、页基类初始化、任务栏页各初始化块、ShowSection 锚定与重绘。空载 Release
基线（6 次 Create 均值，`perf-report.json`）：

| 阶段 | 均值 ms | 说明 |
|---|---:|---|
| child_create（子页 Create 总计） | 222.9 | 其中约 90ms 是 86 个控件 HWND 的模板实例化（无阶段归属） |
| page_base（页基类初始化） | 37.2 | 主体是 86 控件的 SetFont+文本翻译遍历（iterate ≈25ms） |
| 主题/悬停/透明度/圆角填充 | 20.4 | 下拉框逐项插入约 2ms/项 |
| 双击行为下拉填充 | 11.6 | 同上 |
| ShowSection 锚定 | 13.6–22.5 | 86 控件 SetWindowPos+ShowWindow |
| 数字位数下拉填充 | 10.3 | |
| 工具提示创建 | 6.6 | |
| 其余填充（单位/内存/网速上限/显示器枚举/预设菜单等） | ≈19 | |

结论：单项最大成本是模板控件 HWND 创建（约 90ms），其后是基类遍历与各下拉填充；
仅靠延迟填充的收益天花板约 50–60ms。

#### 15.19 托盘图标新增“自动”样式（2026-11-04）

背景：用户反馈“图标的深色和浅色看起来一样”。核实：浅色/深色两套 ICO 共 10 帧、PE 内嵌
两组（349/350）各 10 帧，逐帧字节 0 处相同，平均 RGB 明显不同——资源本身没有问题。
真正原因是旧的 `notify_icon_auto_adapt=true` 开关：开启时浅色/深色两种选择都会被按任务栏
主题覆盖成对比色（浅任务栏→深色图标、深任务栏→浅色图标），两个选项的实际显示效果与
预览完全相同，只有蓝色固定。这是设计冗余。经用户确认，按“蓝/浅/深/自动四选一”根治。

##### 15.19.1 语义与迁移

- 枚举新增 `NOTIFY_ICON_AUTO`；`MAX_NOTIFY_ICON`（资源数组长度）保持 3，另立
  `MAX_NOTIFY_ICON_STYLE=4` 约束样式取值；`m_notify_icon_auto_adapt` 字段与
  `AutoSelectNotifyIcon()` 移除。
- 显示时按需解析：新增 `ResolveNotifyIconForDisplay()`——“自动”在浅任务栏解析为深色
  图标、深任务栏解析为浅色图标，Win10 之前固定深色；静态样式原样返回。
  `GetNotifyIcon` 对“自动”入参先解析再索引资源数组，杜绝越界。
- 配置迁移（LoadConfig）：`notify_icon_style=0..3` 合法（非法值回落蓝色）；旧
  `notify_icon_auto_adapt=true` 且样式非蓝 → 迁移为 3（自动），蓝色保持固定；旧六项索引
  路径同样按旧开关迁移。SaveConfig 写 style 并**移除** `notify_icon_auto_adapt` 键
  （与旧的 notify_icon_selected 键同等待遇），保存/重载对“自动”幂等。
- 主题切换处理与 ApplySettings 不再改写配置：主题变化时“自动”样式直接强制刷新托盘。

##### 15.19.2 界面（IconSelectDlg）
